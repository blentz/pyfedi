## Facts this round's scoping established, all by execution

- **Templates cannot be rendered under the test config.** Any GET that
  re-renders a feed form raises
  `jinja2.exceptions.UndefinedError: 'app.feed.forms.AddCopyFeedForm object' has
  no attribute 'csrf_token'`, because the test config disables CSRF for forms.
  **Patch `app.feed.routes.render_template` and assert on the `form` kwarg** —
  which is also the only way to observe P1.

  with `{'communities': ['This field is required.']}`, and a real value sends
  `form_communities_to_ids` into `search_for_community`, which attempts a live
  webfinger and trips respx with `AllMockedAssertionError`. **Patch
  `app.shared.feed.form_communities_to_ids`.**
- **`apply_feed_url_rules` rejects any url containing a slash**, on both arms, so
  no POST can reach `feed_new:55-56`. That is R2's proof and the reason two
  statements stay uncovered.
- **`feed_unsubscribe` is addressed by feed NAME** (`/feed/<actor>/unsubscribe`).
- `feed_delete` is all but covered already by
  `tests/test_redirect_back.py::TestFeedDeleteRedirect` — one statement and one
  arc remain, the `is_instance_feed` cache bust.

## Task 1: P1 — the NSFL pre-fill

**Pin:** a feed row with `nsfw=False, nsfl=True`, rendered through
`GET /feed/<id>/edit` with `render_template` patched. Assert `form.nsfl.data is
False` **and** `form.nsfw.data is False`, with the row's two columns asserted
different first — a fixture with both flags equal cannot tell the columns apart,
which is the whole reason this defect survived.

**Fix:** `edit_feed_form.nsfl.data = feed_to_edit.nsfl`.

**Invert:** `form.nsfl.data is True` while `form.nsfw.data is False`. Add the
site-disabled rows as a parametrisation: with `enable_nsfl` False the branch
takes the `render_kw` arm instead and `nsfl.data` stays unset — both arms
covered, and the round does not accidentally assert the disabled arm behaves
like the enabled one.

## Task 2: P2 — NSFW/NSFL the site forbids

**Pin:** with `enable_nsfw` and `enable_nsfl` both False, POST `feed_new` with
`nsfw=y, nsfl=y`; assert the created feed carries **both flags True**. That is
the defect. Assert the 302 as well, so the pin also proves the POST succeeded
rather than failing validation for an unrelated reason.

**Fix:** in the route, next to where `g.site` is already read for the widgets,
force each flag off when the site has that switch off. **Do not touch
`make_feed`** — it is floored and closed, and R1 registers the API path's half
of the same question.

**Invert:** the same POST creates a feed with both flags False. Controls: a site
with both switches ON still honours both flags, and a site with exactly one
switch on honours exactly one — three parametrised rows, because a fix that
cleared both flags unconditionally passes a two-row test.

## Task 3: P3 — the missing topic

**Pin:** `GET /feed/new?topic_id=999` raises `AttributeError` — assert the
exception, not a status code, because the test client re-raises by default and
the 500 never reaches the response.

**Fix:** 404 on a topic id that resolves to nothing, matching how the rest of
the file treats a missing feed (`get_or_404`).

**Invert:** the same request returns 404. Control: an existing topic still
pre-fills the form — assert `form.title.data`, `form.url.data` and
`form.communities.data`, which is the block's actual work and is uncovered
today.

## Task 4: P4 — unsubscribing without telling the communities

**Pin:** a user in a remote community joined via the feed, the community's
`subscriptions_count` seeded to a value that is not 1, `send_post_request`
patched. Assert, as the probe did:

- the `CommunityMember` row is gone,
- `send_post_request` was **not** called for the community,
- the community's `subscriptions_count` is **unchanged**.

**Fix:** call `leave_community(community_id=..., src=SRC_WEB)` in place of the
hand-rolled delete, so the route and `leave_feed` agree and **D673**'s guard
covers this caller too.

**Invert:** the membership is gone AND `leave_community` was dispatched for that
community. Assert through a patch on the route's own binding, and add the
control that a community the user joined on their own (`joined_via_feed` False)
is still left alone — that is D673's guard, and it must keep holding here.

**Watch the import.** `app/feed/routes.py` imports `leave_feed` from
`app.shared.feed`; check whether `leave_community` is already imported in this
module before adding an import, and patch it where the route resolves it.
