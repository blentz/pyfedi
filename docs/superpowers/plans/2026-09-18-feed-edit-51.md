## Task 1: P1, P2 and P3 — the private-transition block

**Pin first**, three tests that pass against the current tree:

1. `test_going_private_deletes_every_other_feeds_members` — two feeds, each with
   an owner and a non-owner member, the second owned by a third party. Assert
   the OTHER feed's non-owner row is gone and its owner row survives. Capture
   both ids before the call: the deleted instance raises `ObjectDeletedError`
   when read afterwards, which is how scoping found this.
2. `test_going_private_deletes_the_editors_join_request_not_the_feeds` — a
   pending request from a member and one from the editor. Assert the member's
   survives and the editor's is gone. That is the defect, stated as the claim.
3. `test_going_private_counts_every_feeds_members` — assert
   `subscriptions_count` after the call, with the reason in the docstring: it
   reads 0 today because the global delete emptied the table, so the pin is
   about **which query** produced the number, not the number itself. Pin it by
   asserting the count equals the GLOBAL non-owner count (0) while this feed
   still has an owner row, so the assertion distinguishes global from scoped.

**Then fix**, all three lines together — they are one block and repairing any
one alone leaves a worse bug than it found:

- `:363` gains `FeedMember.feed_id == feed.id`.
- `:364` filters by `feed_id` alone, so the feed's pending requests are cleared
  and the editor's unrelated rows are not.
- `:365` counts **this feed's** `FeedMember` rows, owner included, to match
  `make_feed:228`, which sets 1 for a feed with only its owner.

**Then invert**, with the controls that make each inversion a kill:

- The other feed's member row must survive **and** its count must be untouched.
- A second pending request from a third user on ANOTHER feed must survive.
- `subscriptions_count` must read 1 (the owner) rather than 0, which is the
  number that distinguishes a scoped count from the global one.

## Task 2: P4 — authorize before writing

**Pin first:** a stranger edits a feed they do not own; assert
`Exception('incorrect_login')` **and** that `feed.title` reads the new value in
the session, **and** that a later `db.session.commit()` persists it. The third
assertion is the defect; the first two alone are satisfied by a correct
implementation that merely raised late without a dirty session.

**Then fix:** move the ownership check above the field writes at `:292`. Keep it
inside `if not from_scratch:` — R1 registers that `from_scratch=True` skips it,
and this round pins that behaviour rather than changing it.

**Then invert:** the raise still happens, the title in the session is unchanged,
and a commit afterwards leaves the stored title as it was. Keep a positive
control in the same test file: the owner's edit still lands, and an admin's does
too (`:311`'s second disjunct).

**Ordering note for the implementer.** The check reads `user`, which the
`SRC_API` arm resolves via `authorise_api_user` at `:274` and the web arm at
`:288`. Moving the check above `:292` is safe; moving it above `:274` is not.
